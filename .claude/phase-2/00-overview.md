# Phase 2 — napi Binding Layer. Complete.

`emquad-napi` exposes `emquad-engine` to Node: a dedicated compile thread pool, cache
lifecycle, and the JS boundary. Nothing else — all compilation logic stays in the engine.

**Status: complete.** 64 Rust tests and 32 Node tests pass; clippy, rustfmt, oxlint, and oxfmt
are clean. Phase 3 is now complete too — see [`../phase-3/`](../phase-3/00-overview.md).

Brief: [`../plan/03-phase-2-napi.md`](../plan/03-phase-2-napi.md). Everything in it is
delivered except the worker-process pool, which moved to Phase 3 for a structural reason

## What runs

```sh
cargo test                                       # 64 tests
pnpm --filter @emquad/binding run build          # release addon
pnpm --filter @emquad/binding test               # builds with test-hooks, then 32 Node tests
node packages/binding/bench/pool.js multirun     # throughput vs pool size
./packages/binding/bench/poolcmp.sh multirun     # pinned vs unpinned, one config per process
```

The release build takes several minutes (LTO, `codegen-units = 1`). Debug builds are quick, and
`[profile.dev.package."*"] opt-level = 3` keeps dependencies optimized so the Node suite runs in
about a second rather than several minutes.

**Run the Node suite through its `test` script, not `node --test` directly.** The panic test
needs the `test-hooks` feature, and any later `run build` overwrites the addon without it. The
test asserts the hook exists and says how to rebuild, so the failure is at least legible.


## Two decisions that deviate from the brief

### 1. A failed compile is returned, not thrown

The brief asks for "a real `Error` subclass carrying `file`, `line`, `column`, `hints`, and
`severity`". A promise rejection can only carry a `napi::Error`, which has room for a message
and a status — the structured fields would have to be flattened into a string, and the sync and
async paths would then disagree about shape.

So this layer returns a discriminated result:

```ts
{ ok: true,  pdf, warnings, pages }
{ ok: false, error: { code, message, diagnostics } }
```

**Phase 3 turns the failure branch into the thrown `Error` subclass**, which is where a JS
subclass belongs regardless — you cannot construct one from Rust. Argument and usage errors
*do* throw here, because they are programming mistakes rather than outcomes.

### 2. The worker-process pool moved to Phase 3

Listed as a Phase 2 deliverable, and it cannot be built here. Process isolation means a
*separate OS process* that loads the addon, and we ship a `.node` addon rather than an
executable — so the child has to be a Node process, spawned and supervised by Node. Putting the
orchestration in Rust would mean re-exec'ing Node from Rust with a bootstrap script: all the
machinery, none of the benefit.

It belongs in `@emquad/core`, where `child_process` already exists.

Phase 2 did not merely defer it — it **strengthened the case for it**. See
[`03-findings.md`](03-findings.md): pinning rayon does not rescue the multi-run throughput
collapse, which means the contention is process-global and only process isolation can fix it.
